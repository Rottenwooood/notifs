# notifs · 架构设计

> 设计提案 v0.2 · 2026-11-09

**程序、agent 和人共用一个通信中心，通过订阅配置信息流，通过批量投递控制接收方的触发频率。**

## 1. 它替使用者承担什么

生产者接入一次，之后增加接收者、调整团队关系、换通知渠道，都通过配置完成。中心统一承担分发、积压、重试和批量交付，接收者不用各写一套。

基本结构只有一条：

```text
程序 / agent / 人
        ↓ HTTP 或 IPC
      统一接收
        ↓
      订阅路由
        ↓
    各接收方的队列
        ↓ 按配置攒批、限频
程序入口 / agent 运行时 / 人的渠道
```

## 2. 消息只表达类型和内容

```json
{"type":"test.failed","content":{"failed":2}}
```

也可以直接说话：

```json
{"type":"question","content":"这一步需要你决定"}
```

`type` 提供稳定、廉价的路由依据；`content` 承载完整内容，可以是文本或结构化数据，中心不替业务定义格式。原来的 `type + text` 仍可通过兼容入口使用。

**上一版的字段并非都必要，不能因为将来可能用到，就要求所有消息承担它们：**

- 谁发的，由认证身份确定；消息编号、接收时间由中心生成。
- 发给谁，由订阅决定；明确目标可以通过发送操作指定，只缩小订阅匹配结果，不绕过订阅。
- 重试标识由客户端协议处理；原始 HTTP 调用者需要安全重试时才提供，并在重试中复用。
- 项目、任务、会话、因果链不是所有消息共有的概念，不设为核心字段。业务需要时放在内容中，订阅可以按其中的字段筛选。

不设回复、因果链等额外字段。对话如何组织由参与者决定，中心只负责发布和交付。

## 3. 规则决定通信关系

一条订阅描述：**哪些来源、什么类型或内容条件的消息，交给哪个接收方。** 接收方的投递配置再决定多久触发、一次最多接收多少。

例如，测试失败送给负责实现的 agent；agent 提问送给协调者；人的输入也送给协调者。角色名称只是配置中的目标，核心不内置这些角色。

订阅可以运行中修改。新配置影响后续消息，已经排队的消息保留原目标。多条规则命中同一个接收方时只交付一份。不同模型上下文注册成不同接收目标，避免中心擅自合并上下文。

不再设置独立的发送权限规则。订阅由人和 Last Order 统一管理，普通参与者只发布消息、领取自己的输入。中心通过凭据验证身份，通过订阅决定通信关系。

## 4. 投递控制节奏，保留完整消息

先路由，再按接收方排队和攒批。合并就是一次交付多条原消息，保留内容与顺序，不生成摘要，也不把批次当作新事件重新路由。

每个接收方设置最大等待时间、批大小和触发频率；忙时可暂停接收。不同接收方独立调度，慢渠道不会占住唯一的全局发送流程。

中心确认收下前，消息和投递责任一起持久保存。接收方确认接管后，中心才结束该项投递；失败与断线可以重试。接管不代表任务完成，重投也不保证业务动作只执行一次。

已接受的待投递消息不因超限被丢弃。容量不足时拒绝新提交，由发送者保留并重试。持久化是这套交付机制的保障，不要求参与者靠翻阅不断增长的日志通信。

## 5. 通用性落实在接入边界

HTTP 与本地 IPC 共用接收、路由、排队和确认机制。前者方便脚本和外部服务接入，后者支持本地团队长连接；改变传输不改变业务消息。

适配器负责连接实际参与者：程序接收结构化数据；人的渠道负责显示和回传；agent 适配器把一批输入交给指定运行时，并由宿主决定何时启动模型。

批量交付是否减少模型调用，要由运行时接入保证，不能仅凭中心少发几次就宣称实现。平台凭据、消息渲染和平台回复格式均留在适配器中。第三方通过公开协议接入，无需修改中心。

## 6. 性能优化围绕三个成本

**路由成本：** 配置变更时编译规则、建立索引；消息到达只检查候选规则，不逐条查库、解析配置。任意条件全匹配时仍有遍历成本。

**存储与通信成本：** 正文只保存一份，多目标保存投递引用；批量提交、复用连接、批量发送与确认。扇出仍有目标数量对应的开销，不宣传一次物理写入或零拷贝。

**接收方成本：** 多条消息一次交付，减少运行时唤醒与重复准备上下文；按到期时间调度，避免高频空轮询。

分别测延迟、吞吐、资源占用、扇出成本和实际唤醒次数，在相同可靠性条件下比较。先优化现有实现，不预先决定换语言或自制存储引擎，也不把未经测量的数字写成保证。

## 7. 核心边界与重构方向

实现沿用 TypeScript：主线程处理 Fastify HTTP、Unix socket 和渠道 I/O；独立 Worker 管理身份、编译后的订阅、队列与 SQLite 事务。传输层通过同一组内核操作发布、接收和确认，平台适配器在边缘渲染内容。模型推理、工具执行、任务规划和记忆管理属于使用它的系统。

保留单中心与本地存储的轻量部署。现有监控程序托管作为可选外围功能。重构重点是让路由脱离通知渲染，把渠道扩展为通用接收目标，再加入批量调度与双向运行时接入。

衡量设计是否成立：**增加一种来源、接收者或团队关系，主要改适配器与配置，核心机制保持稳定；使用者因此少维护一套通信逻辑。**
