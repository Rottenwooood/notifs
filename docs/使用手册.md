## 0. 心智模型（30 秒）

它就是一条**事件管道**，中心自己不判断任何业务：

```
源（判断"发生了什么变化"）──POST──▶ 中心（去重 · 规则匹配 · 投递重试）──▶ 出口（弹通知）
```

你要做的永远只有三件事：**建出口 → 建规则 → 让某个程序往这里发事件**。

三个名词，别混：

| 名词 | 是什么 | 谁创建 |
|---|---|---|
| **源（source）** | 一个身份（token）。程序拿它来证明"我是谁" | `nh source add` |
| **出口（channel）** | 通知发到哪（飞书 / 桌面 / 手机 / webhook） | `nh channel add` |
| **规则（rule）** | 什么情况走哪个出口 | `nh rule add` |
| **程序（watcher）** | 判断变化、发 POST 的东西（可选：可托管） | 你 / opencode |

**最常见的坑**：只建了出口、没建规则 → 一条通知都不会有。
出口是"通往哪"，规则是"什么情况走它"。

## 1. 装一次 + 启动

```sh
cd ~/dev/notify-hub

# 装命令行入口（~/.local/bin 已在你的 PATH 里）
ln -sf "$PWD/bin/nh" ~/.local/bin/nh

# 启动中心（前台；自动读 ~/.config/notify-hub/env）
nh start
```

> `nh` = notify-hub 的缩写，和 `pnpm cli` **完全等价**。命令是两层的：`nh <分组> <动作>`。
> `nh`（不带参数）打印完整命令表。
> 仓库里 `monitor` / `producer` 是 `watcher` 的别名，仍可用。

常驻（推荐）：

```sh
mkdir -p ~/.config/systemd/user
cp deploy/notify-hub.service ~/.config/systemd/user/
systemctl --user daemon-reload
systemctl --user enable --now notify-hub
loginctl enable-linger "$USER"        # 未登录也保持运行
journalctl --user -u notify-hub -f    # 看日志
```

**默认只绑 `127.0.0.1:7710`**——只能本机访问（这是刻意的，见第 8 节）。

## 2. 五分钟跑通

```sh
# ① 建出口：桌面通知（本机可见）
nh channel add desktop --kind local --config '{}'

# ② 建规则：什么情况走它（这里 = 全部事件）
nh rule add --name '全部 → 桌面' --when '{}' --actions '[{"channel":"desktop"}]'

# ③ 建信息源，拿 token（**只打印一次**，抄下来）
nh source add demo
```

发一条试试：

```sh
TOKEN=<上一步的 token>
curl -s -X POST http://127.0.0.1:7710/api/v1/events \
  -H "Authorization: Bearer $TOKEN" \
  -H 'content-type: application/json' \
  -d '{"type":"demo.hello","text":"你好 notify-hub"}'
```

桌面弹出通知，`nh deliveries` 能看到一条 `sent`。完事。

想快速建一套演示数据：`nh dev-seed`（upsert 一个 `cli` 源 + `local` 出口 + 一条「全部事件 → 本地」
规则；**不会删除已有数据**，加 `--webhook <url>` 会多建一个 `hook` 出口）。

## 3. CLI 全量速查

### 3.1 看状态

```sh
nh status                       # 一眼看全部：源 / 出口 / 规则 / 程序 / 投递 / 密钥
nh events [--limit 20]          # 最近的事件流
nh deliveries [--status pending|sent|dead] [--limit 20]
nh deliveries retry <id>        # 手动重投一条死信
```

### 3.2 信息源（外部程序的身份）

```sh
nh source add <name> [--dedup-ttl <秒>]   # 新建并打印 token（只显示一次）
nh source list | enable <name> | disable <name> | rm <name>
nh source token <name>                    # 重置并打印新 token（旧 token 立刻失效）
```

- `--dedup-ttl` 默认 `86400`（24h）：同一 `dedup_key` 在这个窗口内只处理一次。
- ⚠️ `nh source add <同名>` 会**覆盖并轮换 token**——别重复跑同一个名字，否则老程序会 401。
- 想一次停掉一批程序：`nh source disable <name>`（它们会收到 403）。

### 3.3 出口（提醒发到哪）

```sh
nh channel add <name> --kind <kind> --config '<json>'
nh channel list | enable <name> | disable <name> | rm <name>
```

`kind` 与最小配置（凭据怎么拿见 [`channels.md`](./channels.md)）：

| kind | 用途 | 配置示例 |
|---|---|---|
| `local` | 本机桌面通知 | `{}` |
| `webhook` | 任意 HTTP 回调 | `{"url":"https://...","headers":{"x-token":"..."}}` |
| `ntfy` | 手机 push（自建/公共） | `{"topic":"nh-7f3a91"}`（自建加 `"server"`） |
| `bark` | iOS push | `{"key":"..."}` |
| `wecom` | 企业微信群机器人 | `{"webhookKey":"abcd-..."}` |
| `feishu` | 飞书群自定义机器人 | `{"webhook":"https://open.feishu.cn/open-apis/bot/v2/hook/..."}` |
| `feishu-app` | 飞书应用机器人（发给某人/某群） | `{"receiveId":"oc_...","receiveIdType":"chat_id"}`（App ID/Secret 从密钥库按名取，默认 `FEISHU_APP_ID` / `FEISHU_APP_SECRET`） |

> 配置里**只写凭据名，不写明文**；明文用 `nh secret set` 存进加密密钥库。

### 3.4 规则（什么情况走哪个出口）

```sh
nh rule add --name <n> --when '<json>' --actions '<json>' [--priority 100] [--exclusive]
nh rule list | enable <name> | disable <name> | rm --name <name>
```

`--when` 的语法（**全部作用于同一条事件**）：

| 键 | 说明 |
|---|---|
| `type` | 事件类型，支持 `*` 通配：`github.*`、`*.error`、`*` |
| `source` | 限定来源（源名，也支持通配） |
| `all` | 字段谓词**全部**成立：`[{field,eq\|ne\|in\|nin\|gt\|lt\|contains\|exists}]` |
| `not` | 任一谓词成立就**排除** |

字段路径可以取 `data.*`、`severity`、`text`、`title` 等。例子：

```sh
# 全部事件
nh rule add --name '全部 → 飞书' --when '{}' --actions '[{"channel":"feishu-notify"}]'

# 只看某一类
nh rule add --name '磁盘告警' --when '{"type":"disk.*"}' \
  --actions '[{"channel":"desktop"}]'

# 带字段条件（severity 是 critical 才响）
nh rule add --name '严重错误' --when '{"type":"app.*","all":[{"field":"severity","eq":"critical"}]}' \
  --actions '[{"channel":"feishu-notify"}]'

# 取值来自 data；not 排除自己
nh rule add --name '别人评论我' \
  --when '{"type":"github.pr.reply","all":[{"field":"data.author","ne":"me"}]}' \
  --actions '[{"channel":"feishu-notify"}]'

# 广播到多个出口
nh rule add --name '全部 → 桌面 + 飞书' --when '{}' \
  --actions '[{"channel":"desktop"},{"channel":"feishu-notify"}]'
```

- `--priority` 越大越先匹配（默认 100）。
- `--exclusive`：这条规则命中后**不再看后面的规则**（用于做"例外优先"）。

⚠️ `throttle`、`quiet` 这些字段在 schema 里有，但**还没实现**（见第 8 节）。现在能用的只有
`--priority` 和 `--exclusive`。

### 3.5 托管程序（watcher）

```sh
nh watcher init <slug> [--kind managed|poller] [--name <显示名>] [--force]
nh watcher check <slug>                    # 静态校验（清单/入口/解释器/凭据）
nh watcher try <slug> [--seconds 15]       # 试运行：真跑一遍，只打印"将会上报什么"
nh watcher sync                            # 扫 producers/*/producer.json 同步进 DB
nh watcher list | enable <slug> | disable <slug> | logs <slug> [--tail 80]
nh watcher rm <slug> [--dir]               # 注销（--dir 连目录一起删）
```

中心替你管这些（托管程序才有）：自动拉起、心跳看护、崩溃退避重启、凭据注入、日志落盘。
目录即期望状态：放进 `producers/` 就生效；删了目录跑一次 `nh watcher sync` 会清记录。

### 3.6 凭据

```sh
nh secret set <名称> [--value <值>]   # 不给 --value 就从 stdin 读（不进 shell 历史）
nh secret list | rm <名称>
```

解析优先级：**加密密钥库 → 同名环境变量 → `NOTIFY_SECRET_<名字>`**。
明文只存一处：密钥库里是 AES-256-GCM 密文，主密钥在 `data/master.key`（600）。
**`master.key` 丢了，库里的凭据就解不开**——备份必须带上它（`nh backup` 会自动带）。

### 3.7 运维

```sh
nh backup [--to <目录>]     # 一致性备份：数据库快照 + 主密钥
nh migrate                  # 建表/迁移（一般不用手动跑）
nh user init | passwd       # 仅 Web 界面需要；纯 CLI 用法不用
nh llm check                # 探测模型端点（只有内置生成 author 才需要）
```

### 3.8 调试

```sh
nh emit --server <base> --token <t> --type <type> --text <text> [--title] [--url] [--dedup-key] [--data '<json>']
nh dev-seed [--webhook <url>]      # 建一套演示数据
```

## 4. 两种程序形态：托管 vs 不托管

程序要往中心 POST，只有两种活法：

| | **托管（managed）** | **不托管（push / 独立脚本）** |
|---|---|---|
| 程序放哪 | `producers/<slug>/`（有 `producer.json`） | **随便哪，中心完全不碰** |
| 需要什么 | 清单 + 入口 | **只要一个 source token** |
| 谁拉起它 | 中心 | **你自己**（cron / systemd timer / 自己的循环） |
| 心跳 / 崩溃重启 / 日志 | 中心管 | 没有 |
| 凭据注入 | 中心加密注入 | 自己保管 |
| 在 `nh status` 里 | 有 | **看不到** |
| 上线动作 | `nh watcher enable <slug>` | 配好 cron/timer 即可 |

### 怎么选

- 需要**登录态、复杂判定、要中心替你兜存活** → **托管**。
- 已经**被别的调度器管着**（cron / systemd timer / CI）、或只是**几行脚本**、
  或你**不想让它进 `producers/`** → **不托管**。
- 只是**轮询一个能直接 HTTP 拿到的接口** → **poller**（连代码都不用写，第 5.3 节）。

### 不托管的三个代价（务必认账）

1. **没人替你调度**：中心不会拉起它。
2. **它死了你不知道**：没心跳、没日志采集、不在 `nh status` 里。
   → 所以脚本里要**主动上报自己的失败**（抓不到数据就发一条事件），否则它会"安静地坏掉"。
3. **凭据自己管**：token 放 600 的文件或环境变量，没有加密注入。

### "统一报警出口"：一个共享源

不想给每个脚本建一个源？建**一个**共用：

```sh
mkdir -p ~/.config/notify-hub
nh source add local                     # 复制打印出来的 token
printf '%s\n' '<token>' > ~/.config/notify-hub/token
chmod 600 ~/.config/notify-hub/token
```

以后任何脚本、服务、设备，只要读这个文件、POST 一下就行。
⚠️ 去重是**按源**算的：共用源时，两个不同脚本发了完全相同的 `type`+`text`，24h 内会被判重。
解法是给 `dedup_key`。

### 5.1 托管程序（managed，中心看护）

```
你是 notify-hub 的监控程序作者。请为下面这个需求写一个"托管式监控程序"。

需求：<一句话说清监控什么、什么算变化、通知里要包含什么 >

硬性前提（不要偏离）：
- 先完整读 docs/producer-protocol.md，它是唯一契约。
- 用 `nh watcher init <slug>` 生成骨架，然后在 producers/<slug>/ 里改：
  - producer.json：填 config（你的参数）、credentials（需要的凭据名，只写名字）、description
  - index.mjs：把 checkOnce() 里的 TODO 换成真实的判定逻辑
- 允许改 command（比如换成 ["python3","monitor.py"]）；换语言也要遵守同一份契约。

程序必须满足：
1) 上报：POST {NOTIFY_BASE_URL}/api/v1/events，body 是 {type,text,...}。
   只有 type 和 text 必填；信封里**不能有未定义字段**（strict，多写会被 400 拒绝）。
2) type 用点分层级，如 github.pr.reply、disk.low。
3) dedup_key 必须"同一件事稳定、不同事不同"，且**带上"这一次执行"的标识**
   （run id / 本次启动时间 / git sha）。不要只用固定前缀（会永远不再提醒），
   也不要用随机值或纯时间戳（会每次重复提醒）。
4) 心跳：每 30s POST {NOTIFY_BASE_URL}/api/v1/producers/{NOTIFY_PRODUCER_ID}/heartbeat，
   body {"status":"ok"}。任何异常（登录态失效 / 页面改版 / 被风控）用
   {"status":"degraded","detail":"..."} 上报——**严禁静默**。
5) 断点、cookie 等写进 NOTIFY_STATE_DIR（自己持久化），进程重启要能续上。
6) 退出码：0 = 正常结束（中心不再重启）；非 0 = 异常（中心按退避重启）。
7) 不硬编码任何密钥；需要的凭据写进 producer.json 的 credentials，值由我用
   `nh secret set <名字>` 存进中心。
8) 一次 POST 最多 100 条；多条用数组。
9) 事件要带"可行动的信息"：完成类事件写清结果/耗时/产物路径，别只写一句"完成了"。

完成标准（你必须自己跑通再交付）：
- `nh watcher check <slug>` 通过
- `nh watcher try <slug> --seconds 15` 能打印出预期会上报的事件
- 给我上线命令，并列出需要我手动做的事（例如存哪个 secret）
- 在 producers/<slug>/README.md 里写清"它会以什么方式坏、我多久能发现"
```

### 5.2 不托管程序（独立脚本，统一出口）

```
你是 notify-hub 的脚本作者。请写一个**独立脚本**：不放进 producers/，不受中心托管，
自己按计划运行，发现变化就 POST 给 notify-hub。

需求：<描述 >
运行方式：<systemd user timer / crontab / 常驻循环；默认用 systemd user timer，每天一次>

前提（我已经准备好了）：
- 中心地址：http://127.0.0.1:7710
- 我的 token 在 ~/.config/notify-hub/token（一行，chmod 600）
- 源名：<name>

程序必须满足：
1) 上报：
   POST http://127.0.0.1:7710/api/v1/events
   -H "Authorization: Bearer $(cat ~/.config/notify-hub/token)"
   -H 'content-type: application/json'
   body: {"type":"...","text":"...", ...}
   只有 type/text 必填；未知字段会被 400 拒绝（strict）。
2) 判重：能给稳定唯一的 dedup_key 就给（含"这一次"的标识）；
   不给则中心按 (源,type,text) 去重 24 小时。
3) 错误处理：
   - 202 {deduplicated:true} = 成功，**不要重试**
   - 400 / 401 / 403 → 记日志并退出非 0，不要傻重试
   - 网络错误 / 5xx → 最多重试 3 次（指数退避）
4) **你要意识到自己是没人看护的**：中心不会拉起你、不会重启你、也看不到你。所以：
   - 必须能被 cron / systemd timer 正常调度（幂等，跑完即退）
   - 状态（游标、上次结果）写到 ~/.local/state/nh-<slug>/，自己持久化
   - 日志写到文件，不要只打 stdout
   - **抓不到数据时，要发一条事件把失败暴露出来**（如 type="script.<slug>.error"），
     不要静默退出——否则你会安静地坏掉，而这是最危险的失败方式
5) 不要硬编码 token，从上面那个文件读。

交付：脚本 + 安装步骤（systemd timer 单元或那一行 crontab）+ 日志/状态路径
+ 怎么手动跑一次测试。
```

## 6. 写程序必须遵守的 8 条（自查表）

- [ ] 事件有 `type` 和 `text`，**没有多余字段**（strict，会被 400）。
- [ ] 每条"可判定为变化"的事件都有**稳定且唯一**的 `dedup_key`。
- [ ] 心跳每 30s 一次（仅托管）。
- [ ] 游标 / 登录态写在 `NOTIFY_STATE_DIR`（托管）或自己的状态目录（不托管），重启能续上。
- [ ] 异常用 `degraded`/`error` 上报，**不静默**（不托管的脚本用一条事件代替心跳）。
- [ ] 不硬编码密钥；托管用 `producer.json` 的 `credentials` 声明，不托管从文件/环境读。
- [ ] 正常结束 `exit 0`，异常 `exit 非0`。
- [ ] 一次 POST ≤ 100 条。

## 7. 三条设计边界（别让中心"学坏"）

中心刻意保持**无状态、单事件匹配**。这是特性，不是缺陷。所以：

1. **进度是"状态"，不是"事件"。**
   只发**稀疏的里程碑**（epoch 每翻倍、每 10%、每 25%），**异常立刻发**（loss 变 NaN、
   被反爬、出现失败条目）。
   `dedup_key` 要带本次执行的标识：`train:<runId>:epoch:100`；
   写成 `epoch:100`（固定值）会让第二次跑实验永远不再提醒。

2. **跨源关联不在中心做。**
   规则里的 "同一个事件上全部成立" 能表达，但"**过去 N 分钟内 A 和 B 都出现过**"不能。
   需要"过去 / 同时 / 累计"这类词，就把逻辑放进程序：
   要么让一个程序同时查两个源（推荐），要么做一个"关联器"——
   用规则把相关事件转发到它的 webhook，它凑齐两条再 POST 一条合成事件。

3. **完成事件要带结论。**
   ❌ `"训练完成"` ／ ✅ `"训练完成 · loss 2.10→0.83 · 用时 3h12m · 模型 ~/models/x.pt"`。
   通知的价值差全在这里。

## 8. 已知边界（现在不做、以及会咬你的地方）

| 边界 | 说明 |
|---|---|
| **只绑本机** | 默认 `127.0.0.1:7710`，远程/公网发不进来。要跨机就改 `NOTIFY_HOST` 或加反向代理。 |
| **无节流 / 静默** | `rule.behavior` 里的 `throttle`/`quiet`/`dedup_ttl` **只是 schema，未实现**。现在实际生效的规则参数只有 `--priority` 和 `--exclusive`。要做"每天最多 3 条"，请在**程序侧**控制。 |
| **投递是"至少一次"** | 崩溃补发在极端情况会重发；消息里带 `event_id`，下游可据此去重。 |
| **去重按源** | 不同源发相同文本不会被去重；共用源才会。 |
| **没有回执闭环** | 通知是单向的，收不到"你点了什么按钮"。想做交互式劝促/确认，得自己补回执通道。 |
| **`at` 不是定时器** | 信封里的 `at` 只是"事件发生时间"标签，**不会延迟投递**。要定时，得让程序自己到点再 POST。 |
| **无内置调度** | 时间类需求（到点提醒、周期任务）都靠程序自己 sleep 或被 cron/timer 调度。 |
| **内置生成可选** | `nh author ...` 需要配模型（`NOTIFY_LLM_*`）；不配也能用上面的全部流程。 |
| **无匿名入口** | 没有 token 一律 401。这是刻意的。 |

环境变量放在 `~/.config/notify-hub/env`（`nh start` 与 systemd 都会读）：
`NOTIFY_HOST` / `NOTIFY_PORT` / `NOTIFY_DATA_DIR` / `NOTIFY_LLM_*` / `NOTIFY_SECRET_<名>`。

## 9. 排错表

| 症状 | 原因 |
|---|---|
| 一条通知都没有 | 没有匹配的**规则**（规则才决定往哪发）；或出口被 disable；或 `when` 不匹配 |
| `401` | token 错 / 缺失（是不是重跑过 `nh source add <同名>` 把 token 换了？） |
| `403` | 源被 disable |
| `400` 且提示未知字段 | 信封里带了规范外的字段（strict） |
| 每次都重复提醒 | `dedup_key` 不稳定（用了随机值/纯时间戳），或超过了源的去重 TTL |
| 提醒过一次就再也不来 | `dedup_key` 是固定值（被永久去重） |
| `nh status` 里找不到我的程序 | 不托管的程序本来就不在（正常） |
| 中心一直重启我的程序 | 非 0 退出 / 没发心跳 / 心跳超时（>90s） |
| 程序在跑但没通知 | 判定逻辑没命中变化；或 `nh watcher try` 时才发现的问题 |
| 端口被占用 | 改 `NOTIFY_PORT` |
| 出口失败反复重试 | 看 `nh deliveries --status dead`，修好后 `nh deliveries retry <id>` |
| 手机收不到 ntfy | topic 拼错，或自建服务器需要 `server`/`token` |

## 10. 停 / 备 / 迁

```sh
# 停
systemctl --user stop notify-hub     # 或前台 Ctrl-C

# 备份（数据库快照 + master.key）
nh backup --to ~/backups/notify-hub-$(date +%F)

# 迁移到新机：带上这三样
#   1) data/               （notify-hub.db + master.key）
#   2) ~/.config/notify-hub/env
#   3) producers/          （托管程序的目录）
# 新机上装好入口后 `nh start` 即可。
```

**自检**：`tools/e2e-resend.sh`（出口失败 → 退避重试 → 最终送达）。
